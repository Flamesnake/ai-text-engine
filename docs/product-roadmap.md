# TaleSpindle 产品路线图

> 状态：产品核心优先。部署方式暂时维持本地程序 + stdio MCP + Skill；在工具契约和数据模型稳定前，不开发插件、远程服务或独立编辑器 UI。

未来分发目标可以包含 DeepSeek Harness 插件，但当前不实现宿主专属封装。核心模型、校验器、评估器、导出器与 MCP 工具应继续保持宿主无关，等产品契约稳定后再增加适配层。

表达自由度的统一边界、受控空间组件和远期 3D 调查实验门槛见 [`narrative-freedom.md`](narrative-freedom.md)。

## 插件就绪门槛

“值得做成插件”不要求走完全部远期路线。开始 DeepSeek Harness 等宿主适配前，核心产品必须同时满足：

- **质量闭环稳定**：结局、失败路径、无效选择、机制回收、walk 完整性和真实 DOM 路线有机器可读结果；同题盲测证明建议与真人体验大致一致；
- **创作契约稳定**：Schema 严格，旧数据有迁移策略，MCP 工具命名和主要返回字段进入兼容期；
- **声画输入安全**：音效与动画使用严格枚举和安全参数，生命周期、静音、减弱动态及无支持环境有测试；
- **具有产品差异**：至少完成阶段 3 的富文本最小纵向切片，使文字本身能表达强调、血字、遮挡和条件揭示，而不仅是普通分支播放器换皮；
- **可部署可诊断**：新用户可完成安装、构建、MCP 注册、自检、创作、验收和单 HTML 交付；错误信息不要求阅读源码；
- **版本可发布**：冻结一个核心数据版本，完成全量测试、代表作品回归、变更日志和最小发布说明。

阶段 4–8 的声景、世界状态、拟态网页、空间调查、3D 和 Meta 不作为首个插件前置条件；它们应在插件化后继续作为宿主无关核心能力演进。插件只负责安装、发现、配置和调用，不复制剧情逻辑、校验器或导出器。

## 产品目标

TaleSpindle 不是通用网页生成器，也不只是分支小说播放器。目标是：

> 让 Agent 使用有限、可靠、可组合、可校验的叙事积木，生成视觉与交互形态明显不同，同时能导出为自包含单文件 HTML 的互动作品。

核心约束：

- 剧情与表现保持结构化数据，不允许 Agent 注入任意 JavaScript/CSS；
- 校验、路径探索和运行时验收能够理解关键逻辑；
- 创作自由用于叙事选择、媒介拟态和节奏，不浪费在重复数据与反复工具往返；
- 导出的 HTML 默认离线可玩、零外部依赖；
- 新能力必须有渐进降级、静音/减弱动态效果等可访问性回退。
- 单文件 HTML 是交付容器而非功能目标；所有新增能力必须服务文字冒险的阅读、选择、调查、关系、推理、解谜、氛围或叙事结构。

## 已完成的基础

- JSON 剧情、变量、条件、物品、文档、证据、推论、关系、秘密、谜题、成就和多结局；
- 静态校验、体验警告、路径探索与运行时验收流程；
- `story_walk` 状态预算、热点诊断和无关 `#visited` 历史剪枝；
- 单文件 HTML 导出；
- 可组合视觉配方：shell、字体、密度、形状、选项风格；
- 短促的 Web Audio 合成音效与基础动画；
- Skill 渐进披露，专项说明按需读取。

## 阶段 1：作品评估与成本观测（核心已完成，待同题盲测）

先建立反馈回路，再继续扩展表现能力。新增能力不得只凭示例作品或主观印象验收。

### 1.1 `story_evaluate`（核心已完成，质量规则继续校准）

新增独立 MCP 工具，返回机器可读指标、解释和非阻断建议，不输出单一“好/坏分数”。至少覆盖：

- 有状态/信息/关系后果的选择比例；
- 单选项节点及连续单选项走廊；
- 重复“返回、查看、继续”类导航标签与高频 hub；
- 关系、谜题、证据和推论是否改变信息、行动或结局；
- 真结局是否回收题目声明的核心机制；
- `sfx`、`fx` 与 presentation 的覆盖、重复、连续强效果和机械铺满；
- 是否只换全局皮肤而没有关键节点演出；
- walk 预算、截断、热点节点和最短结局路径；
- 结构体量：节点、选项、正文字符、证据、推论、谜题与结局。

评估器必须区分“描述事实”和“提出判断”。例如人物剧不因谜题少扣分，探索游戏不因节点多扣分；指标结合 `meta`、实际采用的机制和用户题面，由评估者解释。

#### 验收

- 用至少两部结构和机制重心不同的私有作品建立本地校准快照，但不把作品、路线或专属指标提交到公开仓库；
- 不把 B 题人物关系重心和 C 题多场景探索重心误判成彼此的缺陷；
- 已知问题能被指出：单选走廊、重复导航、机制未回收、特效机械铺满、walk 高风险；
- 输出紧凑，可被 Agent 用于一次集中修订，而不是诱发逐节点机械改稿。

当前已增加无状态原地循环、同节点重复结果，以及未被有效条件、效果或推论链回收的证据、推论与谜题检查。所有此类结果保留为带证据的候选问题，不因纯阅读证据、语气选择或谜题本身具有体验价值而自动判错。

### 1.2 MCP 成本观测（已完成）

记录引擎能观测到的创作开销，不伪装成模型平台的真实 token 账单：

- 每类工具调用次数与耗时；
- 请求/响应 JSON 的 UTF-8 字节数及粗略 token 估算；
- `story_get` 全量读取次数与返回体量；
- 同一节点/资源的重复覆盖次数；
- validate、walk、export 次数与耗时；
- 项目级会话汇总和可清零的观测窗口。

默认不把完整提示或剧情内容写入遥测日志，只记录计数、字节、耗时、项目和资源 id；本地存储，可关闭。

#### 验收

- 能回答“成本主要花在创作、全量读取、返工还是 walk 调试”；
- 不改变 MCP 工具的正常结果和失败语义；
- 日志本身不会造成明显 I/O 或 token 膨胀；
- 提供结构化摘要供同题盲测比较。

### 1.2.1 增量叙事修订（已完成，待盲测校准）

为减少“读取整部作品 → 覆盖整个节点”造成的 token 浪费和并行误改，新增：

- `story_get_node`：读取单个节点和入边；
- `story_review_transitions`：分页返回“源节点末段 → 选项 → response → 目标首段”；
- `story_patch_choice`：局部修改一个选项，并可断言旧 label/target；
- 成本观测分别统计全量读取、单节点读取和转场审查。

工具只标记断链、自环、汇流缺承接等确定性风险，不声称自动判断文风或因果。下一次同题盲测需观察全量 `story_get`、重复节点覆盖和修订请求字节是否下降。

### 1.3 同题双 Agent 盲测（机器侧初评完成，待真人与成本数据）

两个全新 Agent 使用：同一道题、同一模型、同一 Skill、同一引擎版本，不进行人工提示或修正。

记录：真实平台 token（如可获得）、用时、工具调用摘要、最终 JSON/HTML、validate/walk/evaluate 结果、Agent 是否主动运行时验收，以及真人试玩评分。

目的不是选出“最好的 Agent”，而是验证：

- 自动指标是否与真人体验一致；
- Skill 是否让不同 Agent 稳定完成关键验收；
- 相同成本差异来自内容、有效决定、返工还是工具摩擦；
- 同类问题出现两次以上时，应归因给 Skill、MCP、运行时或引擎表达力。

同题双 Agent 的机器侧比较保留在本地评估记录中，不随公开仓库分发。已有样本呈现“开放但状态昂贵”和“收敛但单向”的两端，下一步需结合真人试玩与真实成本决定产品修正优先级。

### 1.4 walk 证明模型拆分（核心已实现，待持续校准）

同题盲测证明，原先单次穷举同时承担“结局可达证明”和“全状态覆盖诊断”，会迫使 Agent 为满足 `truncated === false` 删除原本有价值的自由调查内容。现已将两个目标拆开：

- **结局见证**：为每个结局寻找至少一条可重放的状态与行动路径，输出见证步骤；
- **覆盖诊断**：继续进行预算受限的全状态探索，报告截断、热点、状态维度和未覆盖风险；
- **结果语义**：明确区分“某结局已证明可达”“尚未找到路径”和“全状态覆盖未完成”，不再用一个 `truncated` 覆盖三种结论；
- **目标导向搜索**：研究按结局条件反向排序或多目标搜索，优先找到尚未覆盖结局，而不是反复展开已知 hub 组合；
- **可重放性**：见证路径应能被运行时测试消费，减少 Agent 手工编写七条 DOM 路线的重复工作；
- **保持诚实**：找到所有结局不等于证明没有死路；覆盖截断仍需警告，不能被见证路径掩盖。

当前实现由预算受限的主探索生成覆盖报告；若覆盖不完整，则为每个缺失结局执行独立的目标导向搜索，并输出选择、推论与谜题动作组成的见证。walker 也会记录条件软锁与无结局终点的最短失败见证，并避免把仍可推理或解谜的状态误报为软锁。`story_evaluate` 与 Skill 已改用 `reachability.allEndingsProven` 和 `failures.witnesses` 作为验收门槛，同时把 `coverage.complete` / `failures.complete` 保留为结论完整性诊断。happy-dom 重放器可直接消费两类见证；下一步继续用更开放的未删减样本校准默认预算，并研究无效选择与机制未回收的定向见证。

并行研究少量可验证的结构语义：一次性调查动作、区域完成锚、已问话题和只增不减资源。只有语义明确时 walker 才能合并状态，不采用可能漏掉负条件分支的盲目“超集支配”剪枝。

#### 验收

- 未删减版开放调查样例能在预算内为全部结局找到见证路径；
- 报告仍诚实显示全覆盖是否截断；
- 见证路径可在 `Game` 或 happy-dom 中重放；
- 不因状态合并漏掉 `ne/not_has`、资源消耗、关系下降或提前结案路径；
- Agent 不需要阅读 walker 源码才能理解应修改内容还是仅提高诊断预算。

## 阶段 2：现有声画系统收紧（核心已完成，待代表作品校准）

扩展前先让现有能力可校验、可评价。

### 音效

- `StoryNode.sfx` 已改为与合成器共享的严格枚举，未知音效在写入时拒绝；
- 补齐隐藏结局自动音效，避免 `ending_hidden` 被类型断言掩盖后静默失效；
- `story_evaluate` 已检查全节点重复音效、连续 `drone` 和不必要的手动 click/page/achievement/ending_*；更主观的声画语义错配继续由试玩判断；
- AudioContext 已具备 suspend/resume、主增益即时静音、显式销毁和无支持环境回退测试。

### 文字与动画

- 保留 `prefers-reduced-motion` 回退；
- `story_evaluate` 区分短促事件效果与持续阅读状态，检查长正文上的持续闪烁、抖动、glitch、unstable 与高强度动画；
- `intensity` 限定为 `0.1..2`，`speed` 限定为 `0.25..4`，默认均为 1；越界配置在写入时拒绝。

## 阶段 3：富文本片段与条件揭示（核心已完成，待代表作品校准）

扩展 `blocks`，引入可组合的行内 `segments`。第一批受控样式：

- `emphasis`、`italic`、`blood`、`whisper`；
- `redacted`、`glitch`、`corrupt`、`terminal`、`handwritten`、`broadcast`；
- 条件显示、条件恢复原文和渐进揭示。

乱码/遮挡保存真实原文，并由明确条件决定揭示。条件未满足时真实文本不进入 DOM；占位乱码由文本与位置确定，不改变玩家需要推理的事实。Schema 只接受受控样式，不开放任意 HTML/CSS。

```jsonc
{
  "type": "para",
  "segments": [
    { "text": "病历显示患者于 " },
    {
      "text": "凌晨三点",
      "style": "redacted",
      "revealWhen": { "op": "eq", "var": "#evidence", "value": "e_真实时间" }
    }
  ]
}
```

#### 验收

- 纯文本 `text` 回退仍可玩；
- 条件揭示参与静态引用校验和运行时测试；
- 屏幕阅读器获得可理解文本；
- 动态乱码不会持续影响长文阅读；
- Agent 无需逐字符描述乱码，避免 token 浪费。

## 阶段 4：叙事声景，而非通用作曲器（持续声景核心已完成，待作品校准与音乐动机）

保留现有 `sfx` 作为瞬时反馈，新增持续声景和轻量动机：

```text
UI 音效：点击、翻页、确认
事件音效：心跳、冲击、故障
持续声景：房间、雨、风暴、海浪、广播底噪、电流、通风、引擎、虚空
音乐动机：脆弱、紧张、哀伤、启示、不祥
```

采用短枚举与强度等级，不开放任意振荡器、频率或音符 DSL。相同声景跨节点持续，变化时淡入淡出；`world/phase` 可驱动声景变化。

当前已实现九种程序化持续声景、三级语义强度、全局初始值、节点切换点、`silence`、固定交叉淡化、历史恢复、即时静音与销毁。`story_evaluate` 会报告声景使用并提示同一声景被逐节点重复声明。下一步先用广播站、风暴游艇和失动力飞船三类作品校准听感与音量，再决定是否增加少量音乐动机；`world/phase` 驱动留到阶段 5。

#### 验收

- 一类作品应能形成“寂静—环境增强—事件失控—寂静”的声景弧线；
- 另一类作品应能形成“稳定设备声—记录失真—系统崩坏”的声景弧线；
- 不依赖外部音频文件，保持单文件；
- 静音立即影响所有 audio bus，离开/重开时无悬挂声音；
- 配置保持紧凑，不鼓励全节点重复声明。

## 阶段 5：世界状态与主题转换（核心纵向切片已完成，待作品校准）

在现有变量与条件系统上增加受控表现状态：

- `theme`：作品基础品牌与配色；
- `world`：表世界、里世界或其他叙事位面；
- `phase`：白天、夜晚、警报、断电等阶段；
- `transition`：进入另一状态时的一次性过渡。

世界状态可以改变颜色、纹理、字体稳定程度、HUD、导航、声景和节点表现；不同选项继续由现有 `when` 条件控制。不要把逻辑选择藏进纯 CSS。

当前已实现 `meta.world` / `meta.phase` 状态轴、`effects.world` / `effects.phase` 切换、
`#world` / `#phase` 条件与正文插值，并贯通 schema、存档、walk、validate、evaluate、MCP 和浏览器运行时。
状态外观可覆盖主题、视觉配方与持续声景；切换时播放一次固定过渡，减弱动态偏好下自动关闭。
配置采用“状态级差异覆盖”，避免 Agent 在每个节点重复发送配色和排版。尚待用至少两部作品校准状态优先级、
切换频率与不同外壳组合，确认不会为了换色制造无叙事价值的状态。

#### 验收

- 白天/夜晚或表里世界拥有真正不同的可见行动；
- 存档恢复后逻辑状态与视觉/声景一致；
- walk 能理解决定选项可见性的状态；
- 转换动画在减弱动态效果时安全降级。

## 阶段 6：拟态网页外壳

让界面成为故事世界内的物件。优先研究四种高复用外壳：

- `news`：新闻站、旧闻、快讯、图片说明；
- `forum`：帖子、楼层、折叠回复、用户资料；
- `blog`：文章、归档、标签、隐藏草稿；
- `mail`：邮件列表、线程、附件、草稿。

后续候选：`desktop`、`database`、`wiki`、`store`、`broadcast`。

页面组件必须是结构化类型，能够触发选项、获得证据、解锁文档或改变状态。禁止使用真实品牌登录页、收集凭据、外部追踪请求或任意脚本。

#### 验收

- 初看像正常网页，但所有可交互线索仍可发现、可键盘操作、可验证；
- 网站导航与剧情图共享同一状态真相源；
- 同一作品不需要大量重复页面壳数据；
- 导出仍然离线、单文件、自包含；
- 外壳差异不仅是换色，而是不同的信息组织与交互隐喻。

## 阶段 7：受控空间调查

在文字节点之上增加可选的空间索引，但不建立第二套剧情逻辑：

- 房间、船舱、楼层和区域平面图；
- 可点击、可键盘操作、具有文本列表回退的调查热点；
- 证物近观、翻面、局部放大和前后状态对比；
- 时间线、人物关系图和证据位置图；
- 2D 分层、视差、天气、灯光与有限镜头运动；
- 热点通过现有 `target`、`when` 和 `effects` 映射到节点、证据与世界状态。

优先实现平面图与 2D 热点调查。只有它们在至少两部作品中证明空间表达确实改善调查或推理，并且阶段 3–6 已稳定，才制作一个固定视角、单场景的 3D 调查原型。3D 继续复用现有剧情状态、存档、validate 和 walk，并提供平面图/热点列表回退。

#### 验收

- 视觉热点与文本行动使用同一状态和目标，不产生隐藏分支；
- 唯一关键证据不能只通过鼠标或空间视觉获得；
- 场景声明使用模板与差异覆盖，不重复复制正文和布局；
- `story_evaluate` 能发现无叙事作用热点、不可访问热点和重复场景配置；
- 导出器报告场景、模型、纹理等资源体积；
- 无 Canvas/WebGL、键盘操作和减弱动态模式下仍可完成游戏。

### 远期 3D 原型边界

允许固定摄像机、预设观察角度、有限几何体/灯光/雾、轻量嵌入模型和状态驱动物体变化。暂不允许自由行走、物理、碰撞、战斗、开放世界、任意 shader、Agent 注入 WebGL 代码或完整 3D 关卡编辑。

首个候选实验为单场景“游艇甲板调查”：空间关系需要帮助玩家理解救生艇、航迹、灯塔和舱门证据；若相比平面图没有明显提升真人推理体验，则停止扩展。

## 阶段 8：受控 Meta 与跨周目状态

最后才研究：刷新推进剧情、假结局后页面变化、跨周目记忆、隐藏 URL/错误页、标题页记住上一轮等 Meta 叙事。

必须显式区分：

- 单周目剧情状态；
- 跨周目持久状态；
- 临时界面状态；
- 访问历史。

不得用散落的 `localStorage` 技巧实现。需要 schema、存档迁移、清除进度、隐私说明，以及“单周目可达/跨周目可达”的独立验收模型。

## 明确暂不做

- DeepSeek Harness / Codex / Claude 等宿主专用插件、公共市场发布、远程 MCP、多租户服务；DeepSeek Harness 作为未来优先适配目标记录，但不反向侵入核心层；
- 独立可视化编辑器或完整 IDE；
- Agent 任意输出 HTML、CSS、JavaScript；
- 通用音乐工作站、完整歌曲生成、任意音符/振荡器 DSL；
- base64 大音频默认内嵌、外部 CDN 素材依赖；
- 完整操作系统模拟、多窗口和任意拖拽布局；
- 通用 2D/3D 游戏引擎、自由移动、物理、战斗、开放世界和完整关卡编辑器；
- 依靠页面源码、真实浏览器历史或危险权限才能完成的谜题。

这些项目不是永久否决，但在评估、成本、数据迁移和受控组件基础稳定前不进入实现阶段。

## 跨阶段质量门槛

每一阶段都必须满足：

1. schema 写入边界严格，未知字段/枚举立即报错；
2. 旧 story 能迁移或按明确兼容策略加载；
3. typecheck、单测、构建、MCP 握手通过；
4. 至少一个真实作品完成 happy-dom/浏览器路线验收；
5. `story_validate` 与 walk 不因表现功能丢失逻辑可信度；
6. 新配置采用高层语义和短枚举，避免逐节点重复与 token 浪费；
7. 可访问性、静音、减弱动态和无 AudioContext 环境有回退；
8. 更新 Skill、README、CHANGELOG 和评估样本。
9. 新视觉表面必须具有文本、键盘与低能力环境回退，且不得成为关键逻辑的第二真相源。

## 决策原则

当新功能同时满足以下多数条件时，才值得进入实现：

- 能让多个题材产生真正不同的玩家体验；
- Agent 能用少量结构化字段可靠表达；
- 校验器或运行时测试能够理解；
- 不破坏单文件和离线交付；
- 不需要用户掌握网页编程；
- 在盲测中解决了重复出现的 `ENGINE-LIMIT`，而不是只服务一个样例。
- 能说明它改善了哪一种文字冒险体验，而不只是证明浏览器技术上能够实现。

路线图可根据盲测证据调整顺序，但不得跳过阶段 1 的反馈回路。
